# 夜班章程（NightOps Charter）

> **定位**：本文件是每晚 23:00–09:00 无人值守自动迭代的唯一执行依据。
> **授权**：用户已于 2026-11-19 确认本章程（TASK-0028）。夜间"方案确认"环节由本章程代行：章程授权范围内直接实施，范围外只出提案。
> **修改**：本章程的修改属于工作流调整，必须由用户白天确认，夜间 agent 无权修改本文件。

## 0. 启动检查（每晚第一步，任何一条不过 → 写夜报上报后直接结束）

1. **时间窗**：读本地时钟，必须在 **23:00:00 – 09:00:00** 窗口内（23:00 ≤ t 或 t < 09:00）。越窗（如白天误触发）→ 不做任何事，直接结束。
2. **git 可用**（按顺序探测，取第一个成功者，全失败 → 写夜报上报并结束）：
   - 原生 git：`git --version`
   - **WSL git（本机已验证可用，2.34.1 / Ubuntu-22.04）**：`wsl bash -c "git --version"`；使用时把 Windows 路径映射为 WSL 路径（如 `D:\code\tool_box` → `/mnt/d/code/tool_box`），例如 `wsl bash -c "git -C /mnt/d/code/tool_box status"`。
3. **python 可用**：`python --version` 成功（french-learner 后端等需要）。
4. **仓库干净度**：`git status` 若有未提交变更，先逐文件检查：能对应看板中已确认工作的 → 提交；来历不明 → 夜报记录，**不回滚、不覆盖**，仅在其上继续工作。

预检结果无论成败，都记入当晚夜报。

## 1. 时间窗纪律（醒来模型，用户 2026-11-19 指示"窗口内任何节点都可开始"）

- **触发方式**：自动化在窗口内每 30 分钟醒来一次（23:00 首醒，08:30 末醒）。**窗口内任何一个节点都可启动夜班**：23:00 错过（关机/ZCode 未运行）后，开机后窗口内第一次醒来即自动接手，无需人工干预；用户也可在窗口内手动触发。
- **每次醒来 = 一轮工作循环**：预检（§0）→ 判定首启/续跑 → 领任务实施 → git 提交 → 夜报追加进展 → 结束本轮。
  - **首启判定**：今晚夜报尚不存在，或任务池不是今晚刷新的 → 先巡库（§4.1）再领任务。
  - **续跑判定**：今晚夜报已存在且任务池已刷新 → 直接按优先级领任务，**禁止重复巡库**。
- **本轮结束条件**（均为合法结束，不算早停）：完成一个任务的自然交付边界 / 任务标 blocked / 剩余时间不足以开工新任务（可改做小件或收口本轮）/ 时间窗关闭。未完任务在任务文件记录进度，由后续醒来续做。
- **09:00 硬收口**：本地时间 ≥ 09:00 → 不领新任务，最后一次醒来做全晚总收口（§9）。
- **禁止早停**：不得以"任务难""做不完""等确认"等理由停止工作；每轮必须至少完成一个可交付增量或一个 blocked 判定，不得空转结束。任务池空按 §4.3 补货。

## 2. 白名单：项目文档即授权边界

**授权范围 = 各子项目文档中用户已写明的设计目标。** 具体指：

| 来源 | 夜间可做 |
|------|----------|
| `tools/<工具>/README.md` 及其 `docs/`（架构契约、章程、路线图） | 文档写明的目标、"下一项"、待办方向 |
| `tasks/active/TASK-*.md` | 该任务的需求与验收标准范围内的实现、缺陷修复 |
| `docs/project_content.md` 工具索引中的"状态"列 | 状态注记的遗留事项（如"待前端开发"） |
| 测试失败 / 运行报错 | 修复至绿（天然授权） |

**范围外**（文档没有、用户没说过的新方向、接口/数据口径变更、商业模式类决策）→ 夜间只写提案文件到 `tasks/active/`（命名 `TASK-XXXX-<短名>-proposal.md`，含动机、方案草案、验收标准草案），**不实施**。

### 红线（任何任务、任何理由都不得触碰）

1. 不读取、不修改、不提交 `tools/workbuddy-multi-account/credentials/` 下任何文件（含登录态 token）。
2. 不运行会产生 **GLM/ZHIPU API 真实计费** 的批量生成任务（单元测试一律 mock；annual_report_reader 的真实生成只做单次冒烟且 ≤3 篇）。
3. xhs_crawler **不真机抓取**（风控风险）：只跑 mock/单元测试与本地 Web 界面静态检查。
4. `data/output/`、`data/cache/` 不提交 git；不改 `.gitignore`；不提交任何 `.env`、密钥、凭据文件。
5. 不 force push、不 rebase 已推送历史、不删除他人文件；删除/覆盖任何文件前必须先读其内容确认。
6. 不修改本章程、`AGENTS.md`、`docs/git_guide.md`。
7. 端口被占按各工具既有回退逻辑处理，不杀非本项目的进程。

## 3. 父子 agent 分工

**父 agent（夜班总指挥）**：巡库、排程、派发、审查、git 提交、看板与任务文件维护、夜报。不亲自实现大块代码（单行修复/文档行除外）。

**子 agent（按任务逐个派发，用 Agent 工具）**：

| 角色 | 类型 | 职责 |
|------|------|------|
| 侦察员 | Explore（只读） | 定位 bug 根因、影响面、改动点清单；产出结论不产出文件 |
| 实现者 | general-purpose | 按角色提示词（后端/前端/内容）实现变更 |
| 测试员 | general-purpose | 跑测试 + 对照验收标准逐条核对，给出 PASS/FAIL 及证据 |

**子 agent 提示词必带四条**（逐字写入每次派发）：
1. 禁止调用 AskUserQuestion，无人应答，所有决策自行依据文档做出；
2. 禁止早停，交付物不完整不得结束；
3. 错误按章程第 5 节协议处理：先分析、禁机械重试；
4. 遵守章程第 2 节红线。

## 4. 巡库与任务池（tasks/night_backlog.md）

### 4.1 启动巡库（每晚 23:00 后第一件事，刷新任务池文件）

按顺序采集，写入 `tasks/night_backlog.md`：

1. **红测扫描**：逐工具跑现有测试（有测试就跑；跑不了记录原因，不算失败）。**测试框架约定：一律用标准库 `unittest`**（本机 Python 无 pytest；夜间禁止 pip 安装改动用户环境），运行方式 `python -m unittest ...`。
2. **活动任务推进**：`tasks/active/` 各任务文件中可夜间执行的子项
3. **文档目标**：各工具 README/docs 中"下一项/待办/遗留"目标（白名单来源）
4. **TODO/FIXME 扫描**：`tools/` 下源码中的 TODO/FIXME/HACK
5. **地图一致性**：两张地图 vs 目录实际（多/少文件、索引失效）
6. **提案转化**：昨晚夜报中的"次日建议"若有可执行项

每条登记：编号（NB-NNN）、项目、描述、来源、级别（实施/提案）、优先级。

### 4.2 优先级

红测修复 > 活动任务遗留 > 文档目标迭代 > TODO 清理 > 地图同步 > 提案撰写。
同优先级下轮换项目，保证每晚 5 个子项目都有进展。

### 4.3 任务池耗尽

按第 4.1 节 1-6 重新深度巡库（此时可加大：补测试覆盖、文档补全、跨工具一致性）；仍空 → 撰写提案（范围外方向的方案草案是合法的夜间产出）。

## 5. 错误协议（有错先分析，禁机械重试）

1. **先分析后动手**：报错必须先读完整错误输出 + 相关代码，形成 ≥1 个**书面假设**（写进任务文件变更记录），禁止看一眼报错就改。
2. **一假设一验证**：每个假设只做一次针对性修复并验证；修复必须伴随对假设的印证或证伪结论。
3. **三假设封顶**：连续 3 个假设失败 → 标 `blocked`（记录：报错原文、已试假设、当前最佳猜测、建议），**换下一任务**。
4. **禁止机械重试**：同一命令不带新输入原样重跑 = 违规；超时/网络类错误最多重试 1 次且必须先确认非必现。
5. 单任务 blocked 不影响整体循环：继续领取下一任务直到收口时间。
6. **危险操作即跳过**（用户 2026-11-19 指示）：凡需用户确认的危险操作（批量删除/覆盖非本任务文件、修改系统或全局环境配置、pip 全局安装、git push / force / rebase、真实计费 API 批量调用等），不执行、不询问、不硬试：该任务标 blocked（原因注明"危险操作待用户确认"），**换下一任务继续**，夜报中汇总列出。

## 6. git 规则

- **提交粒度**：每完成一个大的变更或完成一个功能即提交（用户拍板）；不攒大批量。
- **提交前提**：相关测试绿；diff 自查无红线内容（credentials / data/output / 缓存 / .env）。
- **精确暂存**：`git add` 只加**本任务明确改动/新建的文件路径**，禁止 `git add -A` / `git add .`——工作区可能存在用户或其他会话的未提交变更，严禁把它们卷进夜班提交。提交前 `git diff --cached --stat` 逐文件自查。
- **提交信息**：遵循 `docs/git_guide.md`。
- **只 commit 不 push**；push 由用户晨起审夜报后自行决定。
- french-learner 是**独立 Git 仓库**：在其目录内单独提交；tool_box 主仓库仅提交工具索引行变更。
- 首次提交前确认身份配置可用（user.name/user.email；未配置则报预检失败上报，禁止编造身份）。

## 6.1 并行会话风险

白天/夜间都可能有**其他 ZCode 会话在同一仓库工作**。夜班规则：开工前 `git status` 记录基线；只修改、只暂存自己任务触碰的文件；发现他人半成品变更**不回滚、不覆盖、不代为提交**，仅在夜报中记录观察到的路径。若某文件正被他人改动导致冲突，换任务并记录。

## 7. 任务登记（照常走 AGENTS.md 工作流）

- 夜间实施的每个任务：从 `tasks/_TEMPLATE.md` 建任务文件（编号扫描 active+archive 取最大+1）→ 看板登记 → 实施中勾选子任务 → 完成后移入 `tasks/archive/YYYY-MM/` 并更新看板归档表。
- **编号占坑（并行会话防护）**：可能有其他会话同时在领号。任务文件创建后**立即把任务文件与看板行 git 提交占号**，再开始实施；提交时若发现编号已被占用（git 冲突/文件已存在），立即顺延重编号并同步看板，不得使用重复编号。
- "方案确认"环节由本章程第 2 节代行：任务文件"方案（已确认）"节注明"夜间章程代行确认，依据 <文档路径>"。
- **方案选择自主决策**（用户 2026-11-19 指示）：章程第 2 节授权范围内的方案选择（技术选型、实现路径、文件组织、修复方向等）由总指挥分析后**自行选定**，在任务文件"方案（已确认）"节记录备选项与取舍理由；不得因"多种方案待选"而 blocked、等待或询问。
- 提案类产出不建 TASK 编号（或以 -proposal 后缀），晨起由用户定夺后再转正。

## 8. 模型与窗口约束

- 夜班自动化由 Cron 在**窗口内每 30 分钟**触发（`0,30 23,0-8 * * *`，23:00 首醒 / 08:30 末醒），继承工作区默认模型（当前：GLM-5.3-Flash）。
- 白天零触发（cron 时间域已限窗口内）；若白天发现本章程被会话执行（时间窗检查会拦截），属误触发，直接结束即可。

## 9. 夜报（tasks/night_reports/YYYY-MM-DD.md）

每晚收口时写，固定结构（**醒来模型**：每轮醒来在当日夜报追加"## 醒来 HH:MM"进展段；最后一次醒来做全晚总收口汇总）：

```markdown
# 夜报 YYYY-MM-DD
## 预检
<第 0 节结果，逐条>
## 完成项（N）
| # | 项目 | 变更摘要 | 提交 | 测试结论 |
## blocked 项（M）
| # | 项目 | 卡点 | 已试假设 | 建议 |
## 提案项（K）
<文件路径 + 一句话摘要>
## 看板与归档
<新增/归档的任务 ID 列表>
## 次日建议
<1-3 条，给用户的晨间决策输入>
## 配额消耗概况
<完成轮次/子agent 数，粗估>
```

写完夜报后 `git add tasks/night_reports/ tasks/ ...` 一并提交（文档性提交，免测试）。

## 10. 演练模式

用户可随时说"演练夜班"：时间窗检查放行（视为 23:00 窗口内），其余流程完全一致，夜报文件名用 `YYYY-MM-DD-drill.md`。演练同样允许 git 提交（用户已授权）。
