# 2026 A股半年报分析台 — 数据实时更新与成本方案

> 决策问题 A：**数据能否实时自动拉取更新？**
> 决策问题 B：**整体成本是多少？**
>
> 本文基于当前已核实的真实架构撰写，数据基准时点 2026-11-18，报告期 2026H1。
> 涉及金额、套餐、额度均为**量级估算与假设，非任何产品的官方报价**，实际以各服务官方公布为准。

---

## 0. 核心结论速览（TL;DR）

| 决策问题 | 一句话结论 |
| --- | --- |
| **A. 能否实时更新** | **读取侧已是"准实时"**：页面打开时会实时查询资料库在线数据表，资料库一更新，页面无需重新发布即可显示新数据。**写入侧仍是人工**：资料库里的 6 张表由人工导入 CSV，不会自己变。因此"自动更新"的关键在于把"刷新资料库表"这一步自动化——**可落地，推荐用 automation 定时触发**。 |
| **B. 整体成本** | 在低频刷新 + 复用现有免费额度下，**边际成本可接近零**；成本的主要变量是**数据 API 授权**，托管/存储/自动化调度在个人版场景下基本可忽略。 |

**最关键的一句话（直接影响问题 A 的答案）：**
> 页面本身是静态发布页，但它通过资料库 SDK 在**打开时实时读取**在线数据表。所以**更新数据不必重新发布页面、不必换链接**——只要把资料库数据表刷新，页面下次打开就是新数据。这是当前架构最大的优势，也正是"自动更新"可以低成本落地的原因。

## 问题 A：数据能否实时自动拉取更新？

### A.1 先厘清"更新"的三种语义

"能不能实时更新"这个问题，必须先拆成三种完全不同的语义，否则会鸡同鸭讲。

| 语义 | 含义 | 典型频率 | 数据例子 | 当前架构是否适配 |
| --- | --- | --- | --- | --- |
| **① 行情级实时** | 秒/分钟级的价格、资金流、盘口 | 秒~分钟 | 现价、涨跌幅、当日主力净流入 | ❌ 不适配（静态 Page 不适合，见方案3） |
| **② 财报披露级** | 半年报/年报/业绩预告/快报，按交易所披露节奏 | 季频 / 事件驱动 | 营收、净利、ROE、预告类型 | ✅ 适配（定时刷新即可，方案1/2） |
| **③ 数据快照级** | 重新跑一遍查询，把全部指标整体刷新 | 手动或按时 | 6 张表的全量重算与重导 | ✅ 适配（正是人工流水线的自动化目标） |

本系统的定位是**半年报分析台**，核心价值在 **②财报披露级** 与 **③快照级**，这两类完全可以通过自动化解决；只有 **①行情级实时** 需要另起炉灶且不建议做（见 A.2 方案3）。

### A.2 当前架构能做到什么、不能做到什么

**当前数据链路（已核实）：**
```
人工金融检索(NeoData/WeStock/domain_search)
   → 手工整理 6 张 CSV
   → 上传资料库成为 6 个在线数据表(databaseId)
   → 生成 SNAPSHOT_DATA.json → 注入 HTML 内嵌快照
   → 发布为静态 Page
   → 页面打开时通过 __SMART_PAGE__.database.query 实时读数据表，失败降级内嵌快照
```

**✅ 能做到的（读取侧是"准实时"）：**

- **源码级证据（team-lead 已核实）**：`h1_2026.html` 的 `initData()` 在**页面每次加载时**都会通过 `getSDK() → loadAll(databaseId)` 从资料库 6 张在线数据表重新查询数据，并用查询结果**覆盖内嵌的 SNAPSHOT**（脚本第 1062–1087 行）。
- 因此页面读取的是数据表里"当前最新的内容"，而不是写死在 HTML 里的旧快照。
- **三态展示逻辑**（按 SDK 查询结果）：六表全部成功 → 显示"**实时资料库**"徽标；部分成功 → 显示"**混合模式**"徽标；全部失败 → 降级用内嵌离线快照并显示"**离线快照**"徽标。六张表互不影响，单表失败不拖累其他表。
- **由此得出的核心判断：** **页面打开时会实时读取资料库，因此只要资料库数据表被更新，页面无需重新发布、链接不变即可显示新数据。** 静态 Page 架构本身实现了"数据更新与页面展示的解耦"。

> **关键结论（决定问题 A 的答案）：** 需要自动化的其实是"**资料库数据表的更新**"这一环节（重新查询 → 覆盖 6 张 CSV 数据表），而**不是前端页面**。前端实时读取能力已经就绪，自动化只需固化数据刷新流水线即可。

**❌ 做不到的（写入侧仍是人工）：**

- 资料库里的 6 张 CSV **是人工整理并导入的，不会自己变化**。
- 当前没有任何定时/自动机制去"重新查询 → 重做 CSV → 覆盖数据表"。
- 页面内嵌的 `SNAPSHOT` 快照也是人工注入的，不会自动更新（但它只是兜底，主链路走实时查询）。
- 没有事件订阅（如"某公司法半年报披露"自动触发刷新）。
- 不提供真正的秒级行情推送。

> **一句话概括现状：** "读"是实时/准实时的，"写"是人工的。自动化的全部工作，就是把"写"这一端（刷新资料库数据表）从人工变成定时自动。

### A.3 可行的自动化方案（分档）

#### 方案 1（推荐 · 最省力）：automation 定时刷新资料库数据表

**思路：** 用 WorkBuddy 的 automation 定时能力，按 RRULE 周期触发一段 prompt，把现有人工流水线固化为可重复执行的任务：

```
定时触发(RRULE: 每日盘后 / 每半月)
   → 自动重新查询 NeoData / WeStock（走已可用的检索链路）
   → 按 CONTRACT 口径整理并生成 6 张 CSV
   → 覆盖资料库中对应的 6 张在线数据表（按 databaseId）
   → （可选）同步刷新 SNAPSHOT_DATA.json 兜底快照
```

- **页面不变、发布链接不变**：因为页面是打开时实时读资料库，数据表一改，展示即更新。
- **频率建议**：半年报分析台以财报数据为主，建议**每日盘后一次**或**每半月一次**即可；无需高频。
- **需要的前置脚本化工作**（这是方案1的落地成本）：
  1. 把"金融检索 → 6 张 CSV"的人工步骤写成**固定的 prompt 模板 + 数据校验规则**（口径、字段映射、来源标注沿用 CONTRACT）。
  2. 把"CSV → 覆盖资料库数据表"固化为**可重复的写入脚本/工具调用**（按 6 个 databaseId 逐表覆盖，保留表结构）。
  3. 加入**异常保护**：查询失败/数据明显异常时保留旧表并告警，不要用坏数据覆盖好数据。
  4. 记录每次刷新的时间戳与数据源，供页面展示"数据更新时间"。

#### 方案 2（事件驱动）：财报披露季加密刷新

在方案1基础上，针对**披露节奏**动态调整频率：

- 半年报/年报**密集披露期**（如 8 月底、4 月底法定截止日前后）临时提高刷新频率。
- 结合**业绩预告 / 快速报**事件：捕捉到新预告时触发增量刷新，更新表5"业绩预告与待披露观察区"。
- 淡季降回低频，兼顾时效与成本。
- 适合作为方案1的增强项，而非独立方案。

#### 方案 3（真·实时行情）：不建议

若追求**秒/分钟级行情**（现价、实时资金流），当前静态 Page + 资料库查询架构**不适合**：

- 静态发布页没有长连接，需改为**前端轮询 / WebSocket** 直连实时行情 API。
- 会引入**行情源授权、延迟与版权合规、接口限流、前端性能与流量**等一系列问题，成本与合规要求陡增。
- 与本产品"半年报分析"的定位不匹配——财报数据本身按披露节奏更新，秒级刷新没有意义。

> **结论：** 若确需行情级实时，应另立一个"实时看板"独立模块，而非改造本分析台。本分析台**不建议**走此路线。

### A.4 明确的限制与合规边界

- **数据服务授权**：NeoData / WeStock **直连连接器当前未授权**，实际走的是 domain_search 检索链路。自动化刷新同样受此约束，需先把直连授权开通，否则只能依赖检索链路（稳定性/结构化程度较差）。
- **交易所行情版权与延迟**：行情数据受版权与延迟披露规则约束，不得未经授权实时转发。
- **财报数据的可得性**：未披露的数据**不存在于任何合法数据源**——只能等交易所/公司正式披露后才能入库，**不能编造未披露数据**。
- **来源标注**：宏观指标用官方机构名（统计局/央行/海关等），财务指标沿用 CONTRACT 允许的来源组合，不得冒充来源。
- **历史快照要如实标记**：如"待披露未预告"的历史样本须带 `statDate` 与说明，不得伪装成实时数据。

### A.5 最小可落地自动化的步骤清单

按此顺序即可用最小代价跑通"自动更新"：

- [ ] **1.** 开通 NeoData / WeStock 直连授权（或确认继续用检索链路).
- [ ] **2.** 固化"数据查询 → 6 张 CSV"的 prompt 模板与字段口径（直接复用 CONTRACT 的字段映射与来源规则）。
- [ ] **3.** 固化"CSV → 覆盖资料库 6 张表"的写入脚本，按 databaseId 逐表覆盖、保留表结构。
- [ ] **4.** 建立刷新台账：记录每次执行时间、数据源、行数、异常。
- [ ] **5.** 配置 automation：先设为**每日盘后一次**或**每半月一次**（RRULE），验证跑通。
- [ ] **6.** 加入异常保护：查询失败/数据异常则保留旧表并告警，禁止坏数据覆盖。
- [ ] **7.** （可选）页面展示"数据更新时间"，让用户知道数据新鲜度。
- [ ] **8.** （可选）披露季临时加密频率（方案2）。
- [ ] **9.** 观察一个披露周期，确认稳定性后再决定是否加密频率。

## 问题 B：整体成本是多少？

> **重要声明：** 以下均为**量级估算与预算假设，非官方报价**。实际费用取决于所选套餐、调用量、授权范围，**以各服务官方公布为准**。目的是给出成本结构与预算框架，而非精确报价单。

### B.1 分环节成本构成

| 环节 | 成本性质 | 量级估算（假设） | 说明 |
| --- | --- | --- | --- |
| **① 数据获取（API/授权）** | 主要变量 | 从"个人免费额度内 ≈ 0"到"商业/机构授权 年度数千~数万元量级"不等 | NeoData / WeStock / 第三方财经数据 API 有免费额度、套餐订阅、按量计费多种模式。直连授权待开通，具体取决于套餐与数据范围。**这是成本的大头与最大不确定项。** |
| **② LLM 调用** | 按 token 计量，量级很小 | 低频刷新场景下，月度 token 消耗通常在数十万~数百万量级，对应费用多为**元级~几十元/月**（取决于模型与是否生成摘要） | 仅在"用模型整理数据/生成摘要"时产生；纯规则整理可趋近于零。 |
| **③ 存储与托管** | 基本可忽略 | 个人版通常有免费额度，低频小数据量下 ≈ 0 | 资料库存储 + Page 发布托管，数据量（6 表共 200 余行）极小。 |
| **④ 自动化调度** | 一般按触发时资源消耗计 | 低频触发下边际成本低，多含在免费额度内 | automation 本身通常不单独高价收费，成本来自触发时实际消耗的数据查询与 LLM 资源（即环节①②）。 |
| **⑤ 人力 / 维护** | 一次性投入 + 低频运维 | 主要是前期脚本化的一次性投入，之后为口径校验与异常处理的人工 | 自动化后人力从"每次人工重做"降为"偶发校验与排障"。 |

### B.2 三档成本情景

| 情景 | 刷新频率 | 数据源策略 | 成本量级（假设） | 适用 |
| --- | --- | --- | --- | --- |
| **最低档** | 手动 / 每半月 | 复用现有免费额度 + 检索链路，纯规则整理不调 LLM | **接近零边际成本**，主要在免费额度内 | 验证阶段、个人研究、低频需求 |
| **中档（推荐）** | 每日盘后 | 开通数据 API 套餐 + 用 LLM 生成摘要 | 以 **LLM 元级/月 + 数据套餐费**为主；若选个人/低档套餐仍较低 | 常规运营，时效与成本平衡 |
| **较高档** | 高频（小时级/准实时） | 多数据源 + 实时行情 API + WebSocket 前端 | 数据授权与接口调用费显著上升，可达**数千元~数万元/年量级**，且合规成本高 | 专业/商业实时看板，本产品不建议 |

### B.3 成本主要花在哪

> **结论：成本主要花在"数据 API 授权"这一项，其余环节基本可忽略。**

- **数据 API 授权**是唯一的大额、且随频率/数据源数量线性增长的变量；高频与多源是成本失控的主因。
- **存储、托管、自动化调度**在个人版免费额度 + 低频场景下，边际成本接近零。
- **LLM 调用**即便使用，量级也远低于数据授权。
- **人力**主要是一次性的脚本化投入，自动化后持续成本很低。
- 因此，**控制成本的核心杠杆是：控制刷新频率 + 选对数据套餐 + 避免不必要的多源/实时行情**。

## 综合决策建议

1. **问题 A 的答案：能，但要分清层次。** 读取侧已准实时（页面打开实时读资料库、更新数据无需重发页面）；写入侧的人工环节可通过 **automation 定时刷新资料库数据表**低成本自动化。**推荐方案1**，披露季叠加方案2。方案3（秒级行情）不建议。
2. **问题 B 的答案：可控。** 低频 + 免费额度下接近零成本；主要成本在数据 API 授权，其余可忽略。推荐从**最低档起步，验证后升到中档（每日盘后）**。
3. **先决条件：** 开通 NeoData / WeStock 直连授权，并把人工流水线脚本化（prompt 模板 + 写入脚本 + 异常保护）。
4. **合规底线：** 财报数据只在披露后入库，不编造未披露数据；来源如实标注；行情版权与延迟规则严格遵守。
